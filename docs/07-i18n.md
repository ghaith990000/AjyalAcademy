# Internationalization (Arabic / English)

## Setup

- Library: `i18next` + `react-i18next` (`src/lib/i18n.ts`).
- Languages: `ar` (**default**, RTL) and `en` (LTR). Language choice is persisted in `localStorage` under `ajyal.lang` (and in `profiles.preferred_language`: applied once after sign-in, and every later toggle is saved back — see D-037).
- `applyDocumentLanguage` sets `<html lang>` and `<html dir>` on every language change — components never set direction themselves.
- Language toggle lives in the app bar/sidebar and on the login page (`LanguageToggle`, Phase 1). The browser tab / home-screen title follows the language (`applyDocumentLanguage`); the web app manifest carries both names ("Ajyal Academy · أكاديمية أجيال").

## Files

`src/locales/{ar,en}/<namespace>.json` — one namespace per feature (`common`, `auth`, `players`, `subscriptions`, `discounts`, `sessions`, `attendance`, `expenses`, `reports`, `activity`, `settings`, `errors`, `locations`, `applications`, `register`). Register each namespace in `src/lib/i18n-resources.ts` (import both JSON files and add them to `resources`). **Both languages must have identical key sets** — enforced by `src/test/conventions.test.ts`. Current namespaces: `common`, `ui`, `nav`, `auth`, `home`, `dev`, `errors`, `coaches`, `players`, `settings`, `discounts`, `subscriptions`, `sessions`, `attendance`, `expenses`, `reports`, `activity`, `locations`, `pwa` (update, offline and install messages).

## Key naming

`<area>.<element>.<detail>` in camelCase, e.g. `players.form.cpr.label`, `players.form.cpr.error.invalid`, `subscriptions.status.expiringSoon`, `activity:action.player.created` ("<b>{{actor}}</b> added the player <b>{{player}}</b> …"). Use interpolation, never string concatenation. **Avoid plural-suffixed keys** (`_one`, `_other`): Arabic needs six forms and the ar/en parity test compares raw keys, so write count sentences that work for any number with `{{n}}` (D-044). Enum labels: `<enumName>.<value>` (e.g. `expenseCategory.field_rent`).

## Writing rules

- No hard-coded strings in components — including `aria-label`, placeholders, toasts, validation messages (zod messages are keys, translated at render).
- Arabic copy is written natively (Modern Standard Arabic, friendly tone), not machine-literal. Use the glossary in [01-overview.md](01-overview.md) for consistent terms (لاعب، مدرب، اشتراك، باقة، دفعة، حصة تدريبية).
- Keep UI robust to text length: no fixed-width buttons/labels; allow wrapping.

## RTL rules (CSS and layout)

- **Only logical properties/utilities:** `ms-/me-/ps-/pe-`, `start-/end-`, `text-start/text-end`, `border-s/border-e`, `rounded-s/rounded-e`, `inset-inline-*`. Never `left/right/ml/mr/pl/pr/text-left/text-right/rounded-l/rounded-r`. (Enforced: the physical-class guard in `src/test/conventions.test.ts` fails the test suite if any `src/` file uses them.)
- Flex/grid row order flips automatically with `dir`; do not reverse manually.
- **Flip directional icons** (chevrons, arrows, "back") with `rtl:-scale-x-100` (Tailwind `rtl:` variant). Do not flip icons that aren't directional (play, check, football, clock).
- Sidebar, bottom tabs, sheets sliding in, toasts, and breadcrumbs mirror.
- Inputs: phone, CPR, email, codes, and amounts are `dir="ltr"` with `text-start`-aligned appropriately (use `dir="auto"` for free-text names so mixed Arabic/English names render correctly).
- Charts: keep time-series left→right unless a design decision says otherwise (log in decisions).

## Formatting

| Thing   | Rule                                                                                                                                                                                                                                                                                  |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Digits  | **Latin (0–9)** in both languages (matches CPR/phone entry in Bahrain). Formatting uses `en-US` number formatting.                                                                                                                                                                    |
| Money   | `formatBHD(fils, lang)` → `20.000 BD` / `20.000 د.ب` (always 3 decimals). Wrap in `<bdi>` in RTL text.                                                                                                                                                                                |
| Dates   | Gregorian. Display `dd/MM/yyyy` (both languages); month names via `Intl.DateTimeFormat(lang)` (`ar` gives Arabic month names). First day of week: Sunday.                                                                                                                             |
| Times   | 12-hour with am/pm in English (`4:30 PM`); Arabic uses `ص` / `م` via `Intl.DateTimeFormat('ar', { hour: 'numeric', minute: '2-digit' })`, Latin digits. Ranges: `formatTimeRange` inside a plain `<bdi>` — **no `dir="ltr"`** (D-060).                                                |
| Months  | `formatMonthYear(y, m, lang)` → `September 2026` / `سبتمبر 2026`; `formatMonthName(m, lang, 'long' \| 'short')`. Period labels sit in a `<bdi>`.                                                                                                                                      |
| Margin  | `formatMargin(bps, lang)` → `61.11%` / `61.11٪` (Latin digits, two decimals), `—` when there is none; shown in `<bdi dir="ltr">`. Negative money goes through `Money` (D-068).                                                                                                        |
| CSV     | Column names and labels are translated to the admin's current language; dates `yyyy-MM-dd`, amounts `540.000` (no unit), UTF-8 with BOM (D-066).                                                                                                                                      |
| Ago     | `formatTimeAgo(then, now, lang)` → `5 minutes ago` / `قبل 5 دقائق`, `yesterday` / `أمس`, from a week the plain date; `formatRelative(n, unit, lang)` for counting forward (`tomorrow`, `in 5 days`, `خلال 5 أيام`) — platform words, Latin digits, correct plurals in both languages. |
| Phone   | Stored as typed digits (Bahrain 8-digit local numbers; optional `+973`); displayed LTR.                                                                                                                                                                                               |
| Sorting | `localeCompare(lang)` / `Intl.Collator(lang)` for names.                                                                                                                                                                                                                              |

## RTL/i18n checklist per screen

- [ ] All strings via `t()`; keys exist in both `ar` and `en`
- [ ] Renders correctly at 390px in `ar` (RTL) and `en` (LTR)
- [ ] No physical-direction classes
- [ ] Directional icons flip; numbers/phones/CPR stay LTR
- [ ] Long Arabic and long English names don't break the layout

## Typed keys (as built, Phase 1)

`src/lib/i18next.d.ts` types `t()` from the **English** JSON files, so a missing/misspelled key is a TypeScript error. Use `useTranslation('ns')` (or an array of namespaces and `t('ns:key')`), and `ParseKeys<'ns'>` when a key is stored in data (see `src/app/nav.ts`). `useLanguage()` (`src/lib/useLanguage.ts`) returns `{ language, rtl }`. Date/time formatting helpers are in `src/lib/dates.ts` (`formatDate`, `formatLongDate`, `formatTime`); money in `src/lib/money.ts`.

Inputs forced to LTR (`<Input ltr />`) also apply the direction to their wrapper so adornments (show-password button) sit at the LTR end.

## Activity sentences (Phase 7)

Each action has one sentence key `activity:action.<entity>.<verb>` (the action's own name, e.g. `action.player.created`). Sentences carry tags that `ActivityItem` renders: `<b>` a name (semibold `<bdi>`), `<m>` money or a time (plain `<bdi>`), `<d>` a date (`<bdi dir="ltr">`) — so an English name inside an Arabic sentence (or the reverse) never scrambles it. **Arabic uses the passive voice** ("أُضيف اللاعب … بواسطة …", "سُجّلت دفعة …") so the verb never has to agree with the gender of a person we know nothing about; English avoids pronouns for the same reason. Values that the snapshot lacks fall back to words (`activity:fallback.*`) or "—"; an action the app does not know yet reads "<b>actor</b> made a change".

## Locations (Phase 9)

The word is **Location** in English and **الموقع** (plural **المواقع**) in Arabic, everywhere — in the navigation, forms, filters, reports, the CSV headers and the feed (D-084). Location names are entered by admins in either language and shown as typed, inside `<bdi>`. The `locations` namespace also holds the shared select wording (`select.*`, `field.*`, `filter.label`) and the database error messages (`error.location_required`, `error.invalid_location`); each feature adds the same two errors to its own `error.*` group.

## Registration (Phase 10)

- **Two namespaces:** `register` (the public form, its validation and errors, the thank-you screen) and `applications` (the admin review, the WhatsApp messages). The form is the one screen a parent may see, so its wording is plain and it is complete in both languages; the language switch is in its bar and the choice is stored with the request.
- **The parent's language decides the message.** `applications:whatsapp.accepted` / `.rejected` are rendered with `i18n.t(key, { lng: application.language })`, not in the admin's screen language; the preview under the button is shown in the parent's direction. Both texts avoid naming a location (D-093).
- Names and phone numbers typed by parents appear inside `<bdi>` or `dir="auto"` boxes (the phone always `dir="ltr"`); numbers stay Latin in both languages.
