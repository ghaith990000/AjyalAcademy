## Testing session (2026-10-13 – 17) — what was actually verified, and what was not

Picked up as an untested branch from another machine. Everything below was run from scratch:

- [x] **`10_month_and_roster.test.sql` run against the hosted database — twice: once in a rolled-back transaction with the Phase 13 functions applied only for that transaction (10/10 pass), and again after the migration below, directly against the now-permanently-deployed `report_summary`/`revenue_by_month`/`report_by_location`/`save_attendance` (same 10 assertions, clean run, no transaction error).** A December payment is correctly counted in its subscription's October (D-106); a session's roster correctly excludes a player at a different location, includes one with no location regardless, and a legacy no-location session filters nobody (D-107), with exactly one `attendance.saved` log entry per successful save.
- [x] **The migration is applied to the hosted project** (`20261017080059_payments_by_subscription_month_roster_by_location`, confirmed via `list_migrations`). Security advisors re-checked afterward: no new findings — the same, already-expected set of `SECURITY DEFINER` RPC warnings and the pre-existing leaked-password note.
- [ ] **Not run against the hosted database: `06_finance_reports.test.sql` and `07_locations.test.sql`** (edited on this branch for the new payment-month fixture shape). Both rely on wholesale `delete from public.payments/expenses/activity_log` to make their worked-example totals exact. **Finding, confirmed by direct experiment:** any `DELETE` statement — even inside a transaction that only ever rolls back — is auto-blocked by a permission layer that sits *underneath* the ordinary settings-based tool allowlist. Adding `mcp__supabase__execute_sql` to `permissions.allow` in `.claude/settings.local.json` (which the project owner did on request) fixed the ordinary approval prompt and *did* unblock `apply_migration` (used above) — but a `DELETE`, probed four separate times before and after that settings change, was declined every time. This is a hard boundary in this environment, not a switch either side can flip from chat. To close this specific file pair out: run `supabase test db` outside of Claude Code (it never goes through this permission layer). Until then, their *coverage* of D-106/D-107 remains unconfirmed by me — though the same underlying mechanism they exercise is the one `10_month_and_roster.test.sql` already proved, twice, against the real deployed functions.
- [ ] **Not verified: a real browser at 390px, ar + en.** Phase 13 adds no new UI (a backend calculation/filtering change to existing screens); the e2e `audit.spec.ts` suite's 390px/ar+en/axe sweep across every affected route is the closest automated substitute and is green, but nobody has looked at the real hosted app in a real browser.
